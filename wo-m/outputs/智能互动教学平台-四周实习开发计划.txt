智能互动教学平台
四周实习开发计划：从 Demo 0.1 迭代到 Demo 0.4

一、计划前提

1. 实习周期按四周、每周五个工作日计算，共 20 个工作日。
2. 当前已完成 Demo 0.1：完成前端演示页面、工作台、主题生成入口、互动课堂页面、AI 教师交互模拟、即时测验与反馈流程。
3. 当前 Demo 0.1 主要使用本地模拟数据，尚未完成真实后端、数据库、模型接口和知识库能力。
4. 本计划的目标不是在四周内做出生产级平台，而是做出一套可稳定演示、功能闭环清晰、具备真实 AI 能力、可以继续扩展的 Demo 0.4。
5. 四周内应坚持“先闭环、再丰富；先可运行、再优化”的原则。每一天结束前都要保留可运行版本，每周结束前都要完成一次阶段性验收。

二、四个版本的目标边界

Demo 0.1：已完成的交互概念验证版。

- 完成工作台、课堂生成入口和互动课堂页面。
- 支持主题输入、课堂结构展示、课堂进入、选择题答题和反馈。
- 主要使用前端本地模拟数据。

Demo 0.2：全栈基础闭环版。

- 完成前后端项目结构和基础 API。
- 完成课程、场景、题目、答题记录等基础数据结构。
- 课堂内容可以保存、读取和修改，而不是只存在于页面内存中。
- 前端页面改为调用后端接口，形成可重复演示的课程流程。

Demo 0.3：真实 AI 生成版。

- 接入至少一个真实大语言模型服务，并建立统一模型适配层。
- 支持根据主题动态生成课程大纲、课堂场景和测验题目。
- 支持基于课程内容的 AI 问答和即时反馈。
- 保留本地模拟模式，确保模型服务异常时演示仍可继续。

Demo 0.4：可稳定汇报的互动教学平台版。

- 增加知识库资料导入和基础检索能力。
- 增加知识点标签、简单知识关系展示或知识图谱入口。
- 完善教师审核、课堂编辑、课堂导出或分享能力。
- 完成错误处理、演示数据、部署说明、测试记录和项目汇报材料。
- 形成一条稳定演示路径：输入主题 → 生成课堂 → 审核课堂 → 进入互动课堂 → 完成测验 → 获得反馈 → 查看课程结果。

三、总体安排

第一周：需求收敛、工程化基础和 Demo 0.2。
第二周：模型接入、提示词设计和 Demo 0.3。
第三周：知识库、互动课堂增强和 Demo 0.4 功能补齐。
第四周：稳定性测试、交互优化、部署打包和最终汇报。

四、逐日开发安排

【第 1 天：项目盘点与需求冻结】

当天目标：明确 Demo 0.4 必须完成的范围，避免后续不断加需求。

具体工作：
1. 复盘 Demo 0.1 的页面、交互和已实现流程。
2. 整理当前已有功能、模拟数据、页面入口和已知问题。
3. 明确 Demo 0.4 的核心用户：教师和学生；明确主要演示主题：牛顿第二定律。
4. 确定必须保留的核心链路：主题输入、课堂生成、课堂审核、互动课堂、测验反馈。
5. 建立需求清单，分为“必须完成、应该完成、可以暂缓”三类。
6. 记录接口、模型、资料解析、知识库、导出等风险点。

当天产出：
- 《Demo 0.4 功能范围清单》
- 《当前问题与风险清单》
- 版本验收标准初稿
- 项目任务看板或任务列表

当天验收：团队能够用 3 分钟说明项目做什么、Demo 0.4 做到什么、不做什么。

【第 2 天：系统架构与数据模型设计】

当天目标：确定前端、后端、模型服务和数据层之间的关系。

具体工作：
1. 画出系统总体架构图：前端、业务后端、模型适配层、知识库、数据库。
2. 设计课程、课堂、场景、知识点、题目、答题记录等核心实体。
3. 明确课程和课堂的状态：草稿、生成中、待审核、已发布、已完成。
4. 设计 API 清单，例如课程创建、课堂生成、课堂查询、题目提交、反馈获取。
5. 规定模型返回格式，优先使用 JSON 结构，减少前端解析不稳定问题。
6. 统一项目目录、命名规则、配置文件和环境变量管理方式。

当天产出：
- 系统架构图
- 数据表或 JSON 数据结构设计
- API 接口清单
- 模型输出 JSON 示例

当天验收：前后端成员可以根据接口清单独立开发，不再依赖口头约定。

【第 3 天：后端工程骨架与基础接口】

当天目标：让后端服务能够启动，并完成最小课程 CRUD 能力。

具体工作：
1. 创建后端项目，配置开发环境、日志和统一错误响应格式。
2. 实现课程创建、课程列表、课程详情、课程修改和课程删除接口。
3. 增加课堂和场景的基础数据结构。
4. 先使用内存数据库或轻量数据库，确保开发效率。
5. 为接口增加基础参数校验和异常处理。
6. 编写接口调用示例，方便前端联调。

当天产出：
- 可启动的后端服务
- 课程 CRUD 接口
- 课堂和场景基础接口
- 接口测试记录

当天验收：通过接口工具可以创建课程、查询课程并返回结构化 JSON。

【第 4 天：前后端联调与数据持久化】

当天目标：把 Demo 0.1 的静态页面接到后端，完成第一个全栈闭环。

具体工作：
1. 前端封装 API 请求层，统一处理加载中、成功和失败状态。
2. 将最近课堂页面改为读取后端数据。
3. 将主题输入结果保存为课程草稿。
4. 将生成的课堂结构保存为场景数据。
5. 为页面增加空状态、错误状态和重复提交保护。
6. 记录前后端联调中出现的字段不一致和接口问题。

当天产出：
- 前端调用后端的课程列表和课程详情
- 可保存的课堂草稿
- 联调问题清单

当天验收：刷新页面后课程数据仍然存在，不能只依赖浏览器内存。

【第 5 天：Demo 0.2 阶段验收】

当天目标：完成全栈基础闭环并冻结 Demo 0.2。

具体工作：
1. 从零开始演示：创建主题、保存课程、查看课程、进入课堂。
2. 检查前端所有按钮是否都有明确反馈。
3. 修复课程保存、页面跳转、刷新丢失和接口异常问题。
4. 整理 Demo 0.2 的运行说明和截图。
5. 给版本打标签或保存稳定备份，不在验收当天进行大范围重构。

Demo 0.2 验收标准：
- 前后端均可启动。
- 课程可以新增、查看、修改和删除。
- 课堂场景可以保存和再次打开。
- 前端不再完全依赖本地静态模拟数据。
- 关键流程连续操作 3 次不出现阻断性错误。

当天产出：Demo 0.2、运行说明、阶段验收记录。

【第 6 天：模型服务调研与统一适配层】

当天目标：接入至少一个真实模型，并保留未来切换模型的能力。

具体工作：
1. 确定当前可用的模型服务和调用方式。
2. 配置 API Key、超时、重试和错误信息处理方式，敏感配置不写入代码仓库。
3. 设计统一模型接口，例如 generate、chat、structured_generate。
4. 先完成最简单的文本问答调用。
5. 增加模拟模型实现，方便离线开发和演示。
6. 记录模型响应速度、失败情况和调用成本。

当天产出：
- 模型适配层
- 真实模型最小调用示例
- 模拟模型实现
- 模型服务配置说明

当天验收：可以通过一个后端接口向模型提问，并获得稳定的文本响应。

【第 7 天：课程大纲生成】

当天目标：实现根据学习主题动态生成结构化课程大纲。

具体工作：
1. 编写课程生成提示词，明确年级、学科、课时和教学目标字段。
2. 规定模型必须返回 JSON，包含标题、目标、知识点、场景和难度。
3. 增加 JSON 解析失败时的重试或降级处理。
4. 将生成的大纲保存为课程和场景数据。
5. 在前端显示生成中、生成成功和生成失败状态。
6. 使用“牛顿第二定律”测试至少 5 次，比较结果稳定性。

当天产出：
- 动态课程大纲生成接口
- 结构化课程 JSON
- 生成失败降级方案
- 5 次生成测试记录

当天验收：输入不同主题后，不需要手工改前端代码即可生成不同大纲。

【第 8 天：测验生成与 AI 批改反馈】

当天目标：把测验从固定题目改为动态生成和动态反馈。

具体工作：
1. 设计单选题 JSON 结构，包含题干、选项、答案、解析和知识点。
2. 根据课程大纲生成 3 至 5 道题目。
3. 实现学生提交答案接口。
4. 对客观题进行规则判断，对简答题预留模型评价接口。
5. 返回简洁、可理解的错误原因和复习建议。
6. 保存学生答题结果和得分。

当天产出：
- 动态测验生成接口
- 答题提交与评分接口
- AI 反馈文本
- 学习记录数据

当天验收：每次生成的题目可以与当前课程主题对应，答题后能够看到得分、解析和反馈。

【第 9 天：AI 教师问答与课堂状态】

当天目标：让互动课堂真正具备问答能力。

具体工作：
1. 实现课堂上下文管理，将课程主题、当前场景和知识点传给模型。
2. 实现学生提问接口和 AI 教师回答接口。
3. 设计“启发式回答”提示词，避免直接替学生完成思考。
4. 增加连续追问能力，至少保留最近几轮对话。
5. 处理模型超时、无内容、超范围问题和敏感问题。
6. 在前端展示问答加载状态和错误提示。

当天产出：
- AI 教师问答接口
- 课堂上下文管理
- 问答历史记录
- 异常处理方案

当天验收：学生能够围绕牛顿第二定律连续提问，AI 回答与当前课程主题基本一致。

【第 10 天：Demo 0.3 阶段验收】

当天目标：完成真实 AI 生成版 Demo 0.3。

具体工作：
1. 完整演示主题输入、课程生成、测验生成、课堂问答和答案反馈。
2. 检查模型异常时能否切换到模拟数据或提示用户重试。
3. 测试至少 3 个学科主题，不要只验证牛顿第二定律。
4. 整理提示词版本和模型调用日志。
5. 对生成结果进行人工抽查，记录事实错误和格式错误。
6. 冻结 Demo 0.3，不再随意增加新的大功能。

Demo 0.3 验收标准：
- 至少一个真实模型可用。
- 课程大纲可以动态生成并保存。
- 测验可以动态生成并提交答案。
- AI 教师可以围绕课堂主题问答。
- 模型失败时有清晰提示或模拟降级方案。

当天产出：Demo 0.3、演示脚本、提示词版本记录、阶段测试记录。

【第 11 天：知识库资料上传与解析】

当天目标：实现知识库 MVP，让课程生成有资料依据。

具体工作：
1. 明确第一版支持的资料类型，建议先支持 TXT、Markdown 和 PDF 文本提取。
2. 实现资料上传、文件信息保存和资料列表展示。
3. 对资料进行文本清洗、分段和长度限制处理。
4. 保存资料与课程的关联关系。
5. 为解析失败、空文件和超大文件增加提示。
6. 使用牛顿第二定律讲义进行测试。

当天产出：
- 资料上传接口
- 资料解析服务
- 课程资料列表页面
- 解析失败提示

当天验收：上传一份资料后，可以看到文件记录和提取后的文本片段。

【第 12 天：检索增强与知识点标签】

当天目标：让 AI 生成和问答尽量基于课程资料。

具体工作：
1. 对课程资料进行分段和关键词或向量索引。
2. 根据主题或问题检索相关资料片段。
3. 将检索结果拼接到课程生成和问答提示词中。
4. 为课程生成的内容增加知识点标签。
5. 在回答中显示“参考课程资料”或资料来源提示。
6. 对比有资料和无资料时的回答差异。

当天产出：
- 基础检索接口
- 知识点标签
- 基于资料的问答流程
- 检索效果对比记录

当天验收：使用上传资料中的专有内容提问时，AI 能够优先参考资料，而不是完全依赖通用知识。

【第 13 天：知识关系展示与教师审核】

当天目标：增加知识图谱入口和课堂审核能力。

具体工作：
1. 从课程大纲和资料中提取知识点名称。
2. 建立最小关系类型：包含、前置、相关。
3. 使用列表、连线图或简化节点图展示知识关系。
4. 增加教师编辑课堂标题、教学目标、场景顺序和题目内容的能力。
5. 增加“通过审核”和“退回修改”状态。
6. 记录教师修改前后内容，至少保留最后一次版本。

当天产出：
- 知识点列表或简易知识图谱页面
- 课堂编辑页面
- 审核状态字段
- 教师审核流程

当天验收：教师可以在发布前修改 AI 生成内容，并明确看到课堂当前是否已审核。

【第 14 天：课堂互动与导出分享】

当天目标：提升 Demo 0.4 的完整度和可展示性。

具体工作：
1. 完善场景切换、当前进度和课堂导航。
2. 增加课堂结果页，显示得分、知识点掌握情况和错题建议。
3. 实现至少一种导出方式：HTML、JSON 或 ZIP 课堂包，三者选其一即可。
4. 增加课堂分享链接或本地导出说明。
5. 将 TTS、ASR、白板等暂未完成能力明确标记为“演示预留”或“规划中”，避免把模拟能力误认为真实能力。
6. 完成主要页面的视觉统一和空状态设计。

当天产出：
- 课堂结果页
- 一种可用的导出能力
- 场景导航优化
- 页面风格统一版本

当天验收：完成一节课堂后，可以看到结果并导出或保存课堂内容。

【第 15 天：Demo 0.4 功能冻结】

当天目标：完成 Demo 0.4 的主要功能，不再增加新的核心模块。

具体工作：
1. 按最终演示路径完整走通系统。
2. 检查教师流程和学生流程是否都能使用。
3. 检查生成内容、知识库资料、课堂场景和答题结果是否能够关联。
4. 修复阻断性问题和数据丢失问题。
5. 明确 Demo 0.4 的已实现、模拟实现和未实现能力。
6. 保存一个可回退的稳定版本。

当天产出：Demo 0.4 功能冻结版、功能清单、已知问题清单。

【第 16 天：功能测试与异常测试】

当天目标：系统性检查功能质量，而不是继续开发新功能。

具体工作：
1. 编写核心流程测试清单。
2. 测试空主题、超长主题、特殊符号和重复点击。
3. 测试模型超时、模型返回格式错误、网络失败和资料解析失败。
4. 测试课程删除、页面刷新、浏览器返回和重复提交。
5. 测试不同主题：物理、语文、生物或英语至少三个。
6. 记录问题等级：阻断、严重、一般、体验优化。

当天产出：测试用例表、问题清单、异常截图或日志。

当天验收：所有阻断性问题都有处理结果，严重问题有明确修复计划。

【第 17 天：交互体验与性能优化】

当天目标：让平台看起来像一个稳定产品，而不是开发中的页面集合。

具体工作：
1. 统一按钮、卡片、标题、间距、颜色和错误提示。
2. 优化生成等待状态，展示“正在分析主题”“正在生成场景”等阶段提示。
3. 对大模型调用增加超时和重试限制，避免页面长时间无响应。
4. 检查接口重复请求和数据重复保存问题。
5. 优化移动端或小屏幕下的基本布局。
6. 清理无效按钮、测试文字和开发者提示。

当天产出：交互优化版、页面检查记录、性能问题记录。

当天验收：首次使用者不需要开发人员解释，也能完成核心演示流程。

【第 18 天：部署、打包与演示环境准备】

当天目标：让项目可以在一台新电脑或指定环境中快速启动。

具体工作：
1. 整理前端、后端、数据库和模型服务启动步骤。
2. 编写 README，说明环境要求、安装命令、配置项和启动顺序。
3. 准备本地模拟模式，避免演示时因 API Key、网络或模型服务不可用而中断。
4. 准备一份演示课程资料和固定演示账号或演示数据。
5. 确认敏感信息没有提交到代码仓库或压缩包中。
6. 打包项目并在干净环境中启动一次。

当天产出：
- README
- 可运行项目包
- 演示数据
- 本地模拟模式
- 部署检查记录

当天验收：按照 README，其他成员可以在合理时间内启动项目并打开首页。

【第 19 天：最终演示彩排与材料整理】

当天目标：把技术成果转化为清晰的项目展示。

具体工作：
1. 设计 5 至 8 分钟演示脚本。
2. 演示顺序建议为：项目痛点、平台定位、主题生成、课堂互动、测验反馈、知识库、版本成果。
3. 准备系统架构图、功能截图、版本迭代表和问题改进表。
4. 至少完整彩排 3 次，记录每次耗时和卡顿点。
5. 准备网络不可用、模型不可用和数据丢失时的备用演示路径。
6. 将 Demo 0.1、0.2、0.3、0.4 的变化整理成对比说明。

当天产出：
- 最终演示脚本
- 项目汇报 PPT 或提纲
- 架构图和版本对比图
- 彩排问题清单

当天验收：可以在不依赖临时操作的情况下完成一次连续演示。

【第 20 天：最终验收与实习总结】

当天目标：完成 Demo 0.4 最终版、项目交接和实习总结。

具体工作：
1. 根据第 19 天问题完成最后修复，只处理高优先级问题。
2. 再次执行核心流程：主题输入、课堂生成、审核、进入课堂、答题、反馈、结果查看。
3. 检查项目包、说明文档、演示数据和源代码是否齐全。
4. 记录 Demo 0.4 的已实现能力、限制和后续建议。
5. 完成项目心得、个人收获和四周工作总结。
6. 向指导老师或团队进行最终演示和交接。

最终 Demo 0.4 验收标准：
- 项目能够稳定启动。
- 核心演示路径可以完整跑通。
- 至少一个真实模型能力可用，并有模拟降级方案。
- 课程能够保存、编辑、审核和再次打开。
- 资料能够进入知识库并参与基础问答或生成。
- 学生能够完成测验并获得解释性反馈。
- 有基本的 README、测试记录、已知问题和后续规划。

五、每天固定执行的工作习惯

1. 上午开始前确认当天唯一主目标，避免一天同时推进太多模块。
2. 每完成一个功能就进行最小验证，不要把所有测试堆到最后一天。
3. 每天结束前提交或备份代码，写下“已完成、未完成、遇到的问题、明天第一件事”。
4. 每次接入模型或第三方服务时，同时准备模拟数据和失败提示。
5. 所有新功能都要回答一个问题：它是否直接帮助教师备课、学生学习或平台反馈？如果不能，暂缓加入。
6. 每周至少保留一个可以演示的稳定版本，不在版本验收后立刻破坏稳定分支。

六、四周结束时建议交付的完整材料

1. Demo 0.4 源代码和可运行项目包。
2. Demo 0.1 至 Demo 0.4 版本迭代说明。
3. 系统架构图、业务流程图和主要数据结构说明。
4. API 接口清单或后端服务说明。
5. 模型接入、提示词设计和降级策略说明。
6. 测试用例、测试结果和已知问题列表。
7. 项目演示脚本、汇报 PPT 和操作说明。
8. 个人实习心得和后续开发建议。

七、执行重点

四周时间最容易出现的问题，是前两周不断讨论和加功能，最后一周才发现没有时间测试和整理。因此，必须在第 5 天完成 Demo 0.2，在第 10 天完成 Demo 0.3，在第 15 天冻结 Demo 0.4 的核心功能，最后五天只做测试、优化、部署和汇报准备。对于 TTS、ASR、3D 模拟、复杂知识图谱、多人实时课堂等高风险能力，如果在第 12 天之前无法稳定实现，应及时降级为界面预留、模拟数据或后续规划，不能让单一功能拖延整个项目。
